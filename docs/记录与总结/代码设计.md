
# 这里总结一些代码编写规则和设计思路

### 一.必须写业务类的接口
>每个模块的业务应该抽象出一个对外接口，就是正常规范中的service接口或者给业务模块写一个总的接口供其他业务模块，
有的公司业务代码只有实现类没有接口，这样是懒惰不规范的做法。  

>这个对外接口对外提供所有的增删改查等几乎一切的功能方法（包括查询该业务内的一些子表、关联表数据的数据），
其他业务模块使用这个业务模块的时候，只允许通过这个接口调用，不允许直接使用该业务的其他service或mapper调用;  

> 这样如果该模块重新做了一个新版本，或者进行升级功能，需要抛弃掉旧的代码的场景时，只需要写一些新的实现类，都还是使用这个统一接口，就不需要外部重新和该模块做代码对接。


### 二.必须写业务模块单独的异常类
>异常类时可以让开发者立刻定位到时哪个业务模块下的哪个功能报错的。


### 三.大模块之间的调用一定要写中间调用类
>大模块之间的调用不要直接注入对方的某个service使用,更严禁直接使用对方业务的Mapper类或Dao层的类;  
要写一层(或封装一层)中间过渡的调用类(例如xxxServiceApi的类), 这样做,即是为了收窄大模块之间的调用的地方,方便对接,方便问题排查,
方便模块升级改造后不影响其他业务的对接代码(上面的第一条);
另外很重要的一点是为了以后做大模块分拆成单独微服务的时候,方便分离,只要把这一层中间的过渡类,做成一个单独的 API jar包,供双方引用就行了.  
否则业务之间的交叉调用,一层套一层,分都分不开,拆分服务的工作量会很大.
