### kubectl get no 
这会列出所有节点资源以及它们的状态，应为 Ready。如果有任何节点处于 NotReady，你需要检查原因。

#### 加参数:
-o wide:  
例如:kubectl get nodes -o wide  会显示更多详细的信息,包括节点的ip地址等

-w 或 --watch :  
会监视节点的实时状态变化。当某个节点状态改变时，命令行会实时更新显示。非常适合在排查问题时监控节点状态。
kubectl get nodes -w


-l 或 --selector :  
使用标签选择器（label selector）可以根据节点的标签筛选出特定的节点。
就是比如你在yaml文件中给当前要部署的资源(比如Deployment)的labels标签里设置了一些标签,比如name: myNginx或 appName:myNginx, 
在查询Deployment的时候,就可以通过这个参数查询指定的标签的资源.
kubectl get deploy -l appName=myNginx
 
标签选择器非常适用于大型集群管理，可以快速筛选出特定的节点进行操作。下面要学习的Deployment的yaml管理里有通过这个机制去匹配和管理相关的资源.


-o json 或 -o yaml (--output=json 或 --output=yaml) :   
kubectl get nodes -o json  
使用 -o json 或 -o yaml 可以将输出以 JSON 或 YAML 格式显示，这对于调试或者编写自动化脚本非常有用。比如查看某个节点的详细信息，可以这样执行：
kubectl get nodes node-1 -o json

--field-selector <field>
允许你基于节点的字段来筛选输出。例如，选择状态为 Ready 的节点：kubectl get nodes --field-selector status.conditions[0].status=True

那我们写yaml文件的时候一般kind指令里写什么呢? 写pod还是Deployment,或Service?

其实yaml直接的kind里直接写pod是可以的,代表这里yaml管理和部署的直接就是pod, 但是一般直接部署pod类型的资源会有很多问题,
比如这样部署的pod无法随意的扩容等,无法动态的修改里面的一些参数已达到动态管理容器的目的.

所以,一般我们写yaml管理和部署pod是通过Deployment资源类型去统一调度管理pod.
可以把Deployment认为是docker swarm集群里面的service服务,用来统一管理一类容器,这一类容器通常应该就是一个项目下的多个实例.
比如部署nginx的话,就创建一个nginx的Deployment,Deployment下面自动创建并管理者多个nginx的pod,每个pod积极看做是一个nginx的服务实例,
这些实例分布在不同的节点上. pod就可以先看做是docker swarm里面的task任务,是最小的执行单元,一般可以看做是一个容器(当然不完成等于一个容器,pod本身包含容器和一些其他机制)

k8s里面还有一种常用的资源就是service,这个service和docker swarm里的service就不一样了,这个service可以看做是给Deployment定义的一个
与外界访问通信的一套固定元素和机制,比如定义了一个固定的ip,通过这个ip与外界通信,等.

(老师说开发过程中,如果你是无状态的应用就使用Deployment类型编写yaml,如果是有状态的就使用statefulSet类型写yaml,待研究什么意思)

### Deployment
下面讲解Deployment(部署), 我们可以通过yaml编写一个部署, 这个部署yaml文件里面可以定义要部署的所有信息,比如名称,镜像(当然镜像就决定了你部署的到底是什么),副本数,重启策略,
端口,命名空间,工作目录 等等.

那是因为中间还有一层概念:副本集(ReplicaSet,简称RS), 副本集就是多个副本的一个集中控制器, 看下面系统的总结:

总的来说, k8s管理集群管理pod不是一个pod一个pod的管理的,是抽象了几个层级去统一管理和调配pod,
这些层级统一可以叫做控制器,控制器是分多个种类的, 比如deployment(简写deploy), 比如ReplicaSet简称RS, 比如:ReplicationController简称RC,
比如:statefulSet  比如:DaemonSet, 比如JOb和CronJob等.
这些控制器也都资源的一种,因为k8s一切皆资源.

根据一般的用途分类,又可以分类为下面:   

适用于无状态的pod服务的控制器有: deployment,RS,RC   
适用于有状态的pod服务的控制器有: statefulSet     
适用于守护进程的pod服务的控制器有: DaemonSet    
适用于定时任务的pod服务的控制器有: JOb和CronJob   

![img_18.png](img_18.png)

详解:   
RC在1.1版本的时候就已经废弃了, 因为已经被RS替代掉了. 
以为RC的功能就是给固定的pod动态的调整副本数,扩容缩容,但是只能固定给绑定好的pod调整.
而RS是可以灵活指定标签(label selector)去调整符合指定标签的pod分副本数.比较灵活. RS就是RC的升级.
RC在k8s集群中已经没有了,RS还在. 虽然RS还在, 但deployment又对RS做了再次的封装升级, 兼容了RS又加了其他功能,
因此我们工作中使用的就是deployment而不是RS去部署无状态的应用, deployment在创建的时候会自动帮我们创建一层RS,看下图:
![img_19.png](img_19.png)

#### 滚动更新deployment 
上面已经创建好一个deploy了, 这个deploy会自动有一个对应的yaml文件, 如果要滚动更新deploy就可以通过修改其yaml文件(kubectl edit deployment my-nginx-deploy), 修改template.spec.containers.image的镜像版本,
保存后会自动进行滚动更新(为了好观察是否滚动跟新,可以先把副本数(spec.replicas)改成多个,观察多个副本是否有部分在停止并自动重启).

修改deploy的yaml文件:
kubectl edit deployment my-nginx-deploy

会进入yaml的编辑界面,进行编辑(修改spec.replicas副本数为7),保存.

使用kubectl po -o wide 查看是否有7个pod,并且查看是否都已经是running状态.

kubectl rollout history deployment my-nginx-deploy

deployment.apps/my-nginx-deploy

~~~

kubectl rollout undo deployment my-nginx-deploy


回滚到指定编号的版本:
kubectl rollout undo deployment my-nginx-deploy  --to-revision=1

kubectl rollout status deployment my-nginx-deploy

#### Deploy滚动更新的暂停与恢复
Deployment 控制器允许你在应用更新时暂停和恢复更新操作。暂停更新可以帮助你在做出一系列变更之前，先验证环境、观察问题，或者进行其他需要中断滚动更新的任务。在准备好之后，你可以恢复更新操作。

暂停更新:  
kubectl rollout pause deployment <deployment-name>  
在这个命令之后，Deployment 的更新将会被暂停。暂停状态下，即使你修改了 Deployment 的配置，Kubernetes 也不会立即开始滚动更新。
暂停后，你可以安全地进行一系列的配置变更、调试或更新其他关联的资源（如 ConfigMap、Secrets 等），然后再恢复 Deployment 的滚动更新。


恢复更新:  
kubectl rollout resume deployment <deployment-name>  
这会恢复之前被暂停的 Deployment，Kubernetes 将会开始应用你已经配置的变更，并继续滚动更新。

检查 Deployment 状态:  
kubectl rollout status deployment <deployment-name>  
在暂停或恢复操作后，可以使用 kubectl rollout status 来检查 Deployment 的状态，确保操作成功执行。  
你将会看到 Deployment 的当前状态，例如是否正在进行更新，或者 Deployment 处于暂停状态


暂停与恢复 的操作非常适合在以下场景中使用：  
1.多步骤更新：在进行复杂的多步骤更新时，可以先暂停更新，确保每个步骤都正确实施，再恢复更新。
2.避免意外更新：如果你正在修改与应用相关的多个资源（如 Deployment、ConfigMap、Secrets 等），暂停更新可以避免 Kubernetes 在每次变更时自动开始滚动更新，直到你准备好恢复。
3.验证变更：在应用较大或风险较高的变更时，暂停更新可以给你时间验证新的配置或镜像版本是否按预期工作。

### statefulSet
statefulSet用于部署有状态的应用.
![img_22.png](img_22.png)
![img_23.png](img_23.png)

主要特点:
StatefulSet 相比于无状态的 Deployment，具有以下特点：
稳定的网络标识：每个 Pod 都有一个固定的 DNS 名称。即使某个 Pod 重启或迁移到其他节点，仍然会保留相同的网络标识。(比如Redis pod,如果重启之后之后网络ip变了,那我们的java应用怎么连接)
稳定的存储卷：每个 Pod 都拥有独立且持久的存储卷，即使 Pod 被删除，存储卷中的数据也不会丢失。
按序部署和更新：Pod 按照顺序创建（从 0 到 N-1, 必须前一个pod已经正常运行好之后才能创建下一个pod）并且按顺序删除、终止和更新。更新时也是逐个进行，确保应用不会同时更新所有实例,比如部署Redis应该先部署master再部署slave。
按序删除和缩容：Pod 按照编号倒序删除，从最高编号的 Pod 开始。



那StatefulSet怎么做到上面这些特性呢:
他有两个配置,一个叫headless service,一个叫volumeClaimTemplate.

headless service用于DNS(就是域名与ip的映射,但是pod又没有域名,这里就用pod按规则组合出一个固定的DNS名称)管理,给pod一个固定的NDS名称是这样组成的:  
例如，假设 StatefulSet 名为 my-statefulset，Headless Service(Headless Service也是需要单独创建一个的,就像创建一个pod一样) 名为 my-service，则生成的 DNS 名称可能是：  
my-statefulset-0.my-service.namespace.svc.cluster.local
my-statefulset-1.my-service.namespace.svc.cluster.local

0和1代表多个pod的情况下,pod自己的序号,通过序号可以实现有序性. my-statefulset和 my-service必须在同一个命名空间.

通过上面的规则,相当于给pod固定了一个唯一不变的标识(就是NDS名称),比如my-statefulset-0.my-service.namespace.svc.cluster.local就代表一个固定的pod,
既是这个pod挂了重启或重新建出一个pod,也还是使用这个唯一DNS标识. 访问它就是通过这个DNS标识名称访问,而不必担心ip的变化.


volumeClaimTemplate用于创建持久化卷的模版, 模板中定义了持久化的相关配置和参数等, 用于申请一个用于持久化的存储空间.

### 服务发现: Service

![img_33.png](img_33.png)

K8s的Service(缩写是是svc)是Kubernetes中一种抽象概念，用于定义一组Pod的访问策略。
它的主要作用是提供负载均衡和服务发现，使得外部或其他Pod能够稳定地访问一组运行中的Pod，而无需关心这些Pod的具体IP地址。
通过Service，用户可以实现高可用性，确保即使某些Pod被替换或重启，服务依然可用。
常见的Service类型包括ClusterIP、NodePort和LoadBalancer，每种类型适用于不同的场景。

上图是service和endpoint和pod直接的关系,大概的关系是:  
用户创建一个service用于访问一组pod,一般就是通过定义选择器（selector, 就是通过标签匹配的方式做匹配），来匹配一组Pod, 并管理这一批pod, 
那到底一般是怎么匹配pod的呢, 一般pod是通过deployment或statefulset创建的,而一般deployment或statefulset的yaml文件中都定义了labels, 
因此创建出来的pod就具有这些标签, 比如一个用于部署nginx镜像容器的deployment的labels里面定义了一个app=nginx的标签, 那它创建出来的每个pod
都有这个标签, 那就可以在创建service的时候定义该service匹配app=nginx的pod,这样这个service就会匹配上所有这样的pod.
优点该service与该deploy形成了一对一绑定的感觉,但是如果其他deploy的pod也有这个标签的话, 该service也是会匹配上的. 
只不过实际使用中不会把用于匹配的标签随意的乱写,以免和其他pod混乱,导致匹配错乱.  
我想一般应该是一个服务类型(比如nginx或Redis或java的一个微服务)就定义一个deploy,这个deploy就定义一个自己唯一的label用于匹配service.  
一个service一般也会只去匹配一个服务类型. 

大概就是,一个service因标签匹配的关系,就对应匹配着一个deploy下的所有pod,外界或其他服务类型的pod访问这个service的时候,
service就把请求分发到该deploy下的每个pod上,可以做负载均衡分发.

那service的ip端口是固定的,但是该服务pod由于启停替换或扩容缩容的原因,pod的ip是不固定的,甚至一个pod挂了之后并自动创建一个新pod后,
新pod不但ip变了,所在节点也变了. 那service是怎么知道该deploy下的最新的所有pod的ip的呢?

那是因为有endpoint(缩写是np)这个组件,每创建一个service,k8s集群自动创建一个endpoint与该service对应,
这个endpoint的作用就是基于selector标签匹配pod后,收集并管理所有匹配的pod的ip, 这个自动创建的endpoint的名称和service相同. 
endpoint会自动通过iptables的技术与每个节点上的kube-proxy联系,拿到对应pod的ip信息, 通过查看endpoint(kubectl get ep)可以看到其管理的ip列表.

不过老师会所service一般只做横向流量的请求分发,不做纵向流量的请求访问,说是因为service是4层协议的,应用层的,效率低. 这个是什么意思,待研究.

创建和使用service:  
比如创建一个nginx-svc.yaml的文件,文件的内容是:
![img_29.png](img_29.png)
~~~yaml
apiVersion: v1
kind: Service #资源类型为 Service
metadata: 
  name: nginx-svc # Service 名字
  labels: 
    app: nginx #Service 自己本身的标签
spec:
  selector: #匹配哪些 pod 会被该 service 代理
    app: nginx-deploy #所有匹配到这些标签的pod 都可以通过该 service 进行访间
  ports: #端囗映射
    - port: 80 # service 自己的端口，在使用内ip 访问时使用
      targetPort: 80 #目标 pod 的端囗
      name: web #为端口起个名字
  type: NodePort #NodePort的类型,是随机启动一个端口(30000~32767)，映射到 ports 中的端口，该端口是直接绑定在node节点机器上的，且集群中的每一个 node 都会绑定这个端口, 也可以用于将服务暴露给外访问，但是这种方式实际生产环境不推荐，效率低,而且service是四层负载
~~~

kubectl create -f nginx-svc.yaml

#查看 service 信息，然后可以通过 service 的 cluster ip 进行访问

# 查看 pod 信息，通过 pod 的 ip 进行访问
kubectl get po -o wide

# 测试访问,可以创建一个其他服务类型的 pod,进入pod内部, 通过 service name 进行访问上面的nginx(推荐使用服务名访问)
kubectl exec -it xxx -- sh #进入pod   
wget http://nginx-svc  #测试访问nginx服务

#默认在当前 namespace 中访问，如果需要跨 namespace 访问pod，则在 service name后面加上.<namespace>即可  
wget http://nginx-svc.default



基于service访问外部服务:  
上面说了创建一个service,就可以通过这个service访问匹配的所有pod, 那现在如果有这样的需求:
我们的java服务都迁移到k8s集群了,比如order订单服务,给订单服务创建了一个service叫order-svc, 但是订单服务的数据库还没迁移到集群中,
那是不是订单服务的所有pod里都要通过特别的配置一下这个集群外部的数据库的ip地址才能访问数据库呢,这样岂不是很麻烦,
并且以后数据库迁移到集群之后,给数据库创建service之后,是不是又要把order的所有访问配置又改成访问数据库的service进而才回到正常的集群下的正常模式的访问.

其实不用这个麻烦, 即便是数据库不在集群里, 我们也可以在集群中给数据库定义一个service,让这个service指定访问外部的数据库ip就行了.

那怎么给service指定要访问的ip呢? service下管理的ip不是通过endpoint自动获取匹配的pod的ip吗? 难道可以修改这个获取的ip改成外部的ip吗?

其实如果在创建service的时候,yaml中没有指定(selector),就是不指定要匹配的pod,那创建的service就不会自动创建一个对应的endpoint,
也自然没有pod的ip可收集, 这个时候就可以通过yaml手动给该service创建一个endpoint,在endpoint的yaml中指定要访问的外部服务的ip端口或域名,
那这个service就是能访问集群外部的服务, 因此其实service的访问功能是可以灵活定制的,是可以定制成访问外部的,不一定必须访问集群中的pod, 
定制该service访问外部之后, 在集群中,订单服务和正常一样只需要请求这个service就可以就可以访问外部的数据库或其他服务了.
手动创建的endpoint只要指定和service一样的名称就和service做一一对应了,并且这样的endpoint可以灵活指定要访问的外部的p或是域名,
这样的好处是,如果以后外部的数据库服务迁移到集群中了,只需要修改一下这个service的endpoint里的访问ip就行了,不需要修改需改所有需要访问数据库的订单服务的配置.

### ingress

![img_32.png](img_32.png)

Kubernetes中的Ingress是一种API对象，用于管理外部HTTP和HTTPS流量到集群内部服务的访问。
Ingress提供了一种灵活且可扩展的方式来路由流量，支持多种路由规则，适用于微服务架构中的多种场景。
Ingress允许用户定义如何将外部请求路由到集群内的不同Service。
它通常与Ingress Controller配合使用(这里的老师是的概念就是: 如果把k8s集群体系类比成我们传统方式搭建的微服务架构,
那Ingress的角色就类似我们平常使用的nginx的作用,进行流量的请求分发, 而Ingress本质是这个功能的一个抽象,是一套规则,就像java的接口一样, 
因此具体干这个活的是Ingress Controller这个具体的实现,Ingress Controller实现有很多种,其实Ingress的一个常用的实现其中之一就是nginx, 
叫做Ingress-nginx,在官网可以下载安装, )， 
Ingress Controller负责实际处理进入集群的流量。
